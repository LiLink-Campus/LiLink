# Isolated release checks

These scripts reject the production database and API. Local credentials and target manifests belong under the ignored `artifacts/questionnaire-release-20260920/` directory. Validate Neon project, branch and compute metadata before writing a target manifest. Never commit connection strings, keys, backups or runtime logs.

`node scripts/release/local-rehearsal.mjs start` builds the committed API using the production Dockerfile, starts task-labelled containers with 2 CPUs / 3.5 GiB memory and Mailpit, and exposes the authenticated proxy through Caddy on `http://127.0.0.1:4080`. Set `RELEASE_CADDY_BINARY` to the checksum-verified Caddy 2.11.4 executable; its gzip/zstd configuration matches the observed production gateway. The runner also requires the verified synthetic target and existing restricted credential files. Run `matching`, `evidence`, then `stop` as separate subcommands. Stop removes only the recorded task-owned proxy/Caddy processes, containers and network; it retains logs and database evidence. On Apple Silicon the API is Linux arm64 and Caddy runs on macOS outside the API resource limit, so record both differences from production amd64. The GitHub rehearsal is manual to avoid starting an unused remote API on every push.

Before a matching replay, unfinished `release_worker_*` cycles are retained as DRAFT and pending synthetic match mail is retired. New fixtures also remain DRAFT until all participations exist, then become OPEN within the preparation timer so ordinary cron cannot process partial fixtures. Completed REVEALED cycles and their snapshots remain visible; their existing pair exclusions are retained. The three original synthetic history cycles remain unchanged. Each result reports its actual candidate count. Preparation over 60 seconds fails the workflow after all business assertions have been checked.

Each matching stage waits for every outbox row to become SENT and reconciles the new Mailpit receipts against all expected recipients before advancing. Mailpit retains 20,000 messages so the three stages cannot silently evict the receipts being checked. A repeated tick must not reveal the cycle again. The API logs reveal transaction and snapshot durations separately. The preload observer reports connection-pool occupancy, checkout wait and query round-trip durations without logging SQL text, parameters or credentials.

`database.mjs` provides the guarded audit, encrypted backup, migration and restore rehearsal. `seed-load.mjs` requires the dedicated synthetic Neon project and creates 2,000 synthetic users. `matching-rehearsal.mjs` exercises the running API at 500, 1,000 and 2,000 participants and verifies matching, introduction and snapshot counts. Its output must be captured with Bash `set -euo pipefail` when piped through `tee`.

`load.js` requires **absolute** `TARGET_FILE`, `ACCESS_FILE`, `QUESTION_FIXTURE` and `SUMMARY_FILE` paths, plus the API's exact `RELEASE_SHA`. It verifies the remote identity before generating traffic. Use the official k6 binary. Keep normal production throttle settings.

The authenticated identity endpoint returns 503 unless the upstream API health response is valid. After restarting the API, wait for actual readiness; Docker accepting a restart does not prove migration or application startup succeeded. Connection failures are also counted in proxy logs. SSR checks must confirm the expected rendered heading and user, reject streamed server errors, and verify a live authenticated API read before starting the arrival schedule.

| Mode | Arrival unit | Work per iteration |
| --- | --- | --- |
| `read` (default) | API requests | One of four individual component APIs, equal weighting |
| `home` | Users entering the homepage | One `/me/page-bootstrap/home` read; identity, dashboard and questionnaire summary must be present |
| `match` | Users entering the match page directly | Bootstrap API with the expected user and dashboard |
| `mixed` | Business operations | 70% reads, 20% questionnaire submit + readback, 10% opt-in + readback; 1.3 API requests per iteration on average |

Use `MODE=home LOAD_RATE=500 RATE_TIME_UNIT=1m LOAD_DURATION_SECONDS=120` to model 500 homepage entrants per minute (about 8.3 API requests/s), and repeat with 1,000 entrants/minute. Direct match entry has a different request count. These are API flow measurements; they do not replace browser rendering or Vercel SSR tests.

`load-ssr.js` measures full HTML from the isolated Vercel alias, using `MODE=ssr-home` or `MODE=ssr-match` and `RATE_TIME_UNIT=1m`. In addition to the target, key, summary and release inputs above, provide absolute `SSR_COOKIES_FILE`, `SSR_EXPECTED_FILE` and `SSR_IDENTITY_FILE` paths. The expected file is an independently reviewed candidate configuration with `sha`, `projectId`, `branch`, `alias`, and `deploymentId`; do not generate it by copying the actual identity. The actual identity must come from a fresh deployment lookup. The restricted cookie file contains only the temporary alias-scoped `_vercel_jwt` cookie. Build the identity manifest from fresh Vercel API responses for the alias and deployment: `sha`, `projectId`, `branch`, `state`, `alias`, and `deploymentId`. Require the exact candidate commit on both frontend and API, READY state, and the fixed isolated project and a dated `https://release-YYYYMMDD.lilink.top` alias. The obsolete `release-20260920` alias is rejected. All five identity fields must exactly match the independent expected configuration; arbitrary project IDs and production URLs remain forbidden. This is configuration validation, not live Vercel attestation: obtain and verify the actual manifest before each run. Never use a production or project-wide protection bypass. Run a low-rate smoke check before 500/1,000 entrants per minute; revoke the alias bypass and remove any temporary CI secrets afterward. Full HTML timing and headings supplement the separate Chromium/WebKit user-flow checks.

For protocol capacity, use `MODE=read RATE_TIME_UNIT=1s LOAD_RATE=33` (then 67 and 100). The script permits at most 200 planned API requests/s and 1,800 seconds per run. `MODE=mixed LOAD_RATE=100` means about 130 API requests/s; use the reported `expectedRequests` rather than calling it 100 requests/s.

Every result reports planned iterations/API requests, attempted and successful API requests, completed business iterations, and distinct successful fixture users on their first pass. `home` and `match` also enforce complete API flow latency. Raw `read` users are users with one successful fixture request, not completed browser visits. Unexpected 429 responses and dropped iterations fail the run. The first pass user count is a conservative lower bound after the 2,000 fixtures are reused.

Reconcile request counts and route ratios with `requests.jsonl` from the isolated proxy. Compare them only over the same test time interval, excluding identity checks and other rehearsal steps. Vercel SSR requests require API-side logs because the browser Network panel does not contain those calls.

`benchmark-worker.mjs` runs only the CPU solver and checks pair uniqueness. Its runtime and memory numbers are not end-to-end capacity evidence. Record image SHA, platform, CPU/memory limits, Neon settings, cold/warm state, database wait/lock metrics and outbox completion separately before approving a production release.

The Mac runner also accepts the empty synthetic database `lilink_load_20260921` on the isolated restore-rehearsal branch, using only its dedicated `release_mac_20260921` role. `targets.mjs` fixes the allowed project, branch, host, database and role; the copied `neondb` on that branch is explicitly rejected. Set absolute `RELEASE_TARGET_FILE` and `RELEASE_DATABASE_FILE` paths to the corresponding restricted manifest and connection file. The Mac proxy includes the database in its identity, and k6 checks that identity before generating traffic. This database has no production user rows.

For capacity and soak checks, use `RELEASE_NORMAL_JOBS=true` to include ordinary cron and outbox activity. The matching driver records whether its tick or the scheduler completed preparation and verifies the database terminal state in either case; HTTP success alone is insufficient. Without normal jobs, its tick must explicitly report completion. Mail remains restricted to Mailpit in both modes. If concurrent read load fails, create `artifacts/release-output/stop-matching`; the driver finishes reconciling the current stage's already queued mail and refuses the next stage. Remove this task-owned stop marker explicitly before a new run.

`RELEASE_DATABASE_CONNECTION_LIMIT` sets the isolated API pool size (default 20, bounded to 1–80). Record this setting beside each result. Check the target database's live connection budget before increasing it, including additional application processes and operational connections. A test override does not change production settings.

Run `node --test scripts/release/targets.test.mjs` for identity safety checks. SSR HTML timing excludes hydration and artwork readiness; use `node scripts/e2e/run.mjs e2e/specs/loading-performance.spec.ts` for complete first-screen evidence. No remote load target is provisioned or authorized by changing these scripts.
