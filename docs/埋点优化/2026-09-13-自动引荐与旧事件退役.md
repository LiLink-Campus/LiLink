# 自动引荐与旧事件退役

> 历史记录：自建产品埋点已于 2026-09-16 退役，当前状态见 [后台精简与自建埋点退役](./2026-09-16-后台精简与自建埋点退役.md)。

> **文档归属**：本记录属于 [埋点优化](./README.md)。2026-09-13 本地工作区实现记录；不代表已发布到生产。

匹配揭晓现在自动冻结双方联系方式并生成引荐通知，无需用户再申请联系方式。原来的“点击申请 → 申请成功”漏斗与当前产品行为不符，已替换为以下两个独立指标。

| 事件 | 触发事实 | 计数与边界 |
| --- | --- | --- |
| `match_contact_copy_clicked` | 用户点击匹配页的复制联系方式按钮 | Web intent；每次点击记录，不证明剪贴板成功、添加好友或双方已联系。仅保存 `matchId`、viewport 等白名单字段，不保存联系方式。 |
| `match_introduction_queued` | 自动揭晓事务同时保存引荐时间、冻结联系方式和双方通知 outbox | API outcome；按 MatchParticipant ID 幂等，每个匹配收件人 1 次。2 人匹配通常产生 2 个事件；不代表 SMTP 接受、收件箱送达或阅读。 |

`dashboard_page_viewed`、`match_page_viewed` 继续记录页面曝光。后台“匹配浏览与复制”按时间窗显示曝光和点击次数，关闭该区域的百分比及“环比上一步”展示，避免把重复操作当成逐人转化。“自动引荐通知入队”作为独立 KPI 展示，明确标注尚未接入送达、阅读与实际联系结果。

## 写入与补偿

- 自动揭晓在同一 PostgreSQL 事务内写入 Match、MatchParticipant、OutboundEmail、ProductEventOutbox；任何写入失败，整个揭晓回滚，可重试。
- 事件 ID 为 `match_introduction_queued:<participantId>`，重试或并发揭晓不会产生重复事件。测试用户在 API 排除。
- 原有产品事件 outbox 定时消费和故障重试继续使用。新增事件入队会延长消费窗口，避免服务空闲时跳过刚产生的事件。
- 每日补偿检查近 60 天 `introducedAt`，且必须同时找到该匹配的两条 `match-reveal:<matchId>:0/1` 通知记录，才修复自动引荐事件；仅有历史手动引荐时间不满足条件。补偿保留原 introducedAt 作为 occurredAt，幂等 ID 与首次写入一致。
- 邮件即使后来失败或被取消，仍曾入队，故本指标仍为“入队”，不能用于算送达率。

## 退役范围

移除旧 `match_contact_request_clicked`、`match_contact_requested` 与全部 9 个 `meetup_*` 的共享写入契约、浏览器采集助手、服务端 producer / 补偿扫描及后台约见漏斗。正式运行契约现在共 8 个事件：4 个曝光、2 个意图、2 个结果。优惠券事件继续保留。

历史 ProductEvent、AuditLog 和见面业务记录不在此次代码清理中删除或重写。旧事件不再接收新上报，不用新名称重标历史点击。旧事件 outbox 的待处理任务按功能退役处理；该变更不延长原有的事件保留期限。

## 验证

已通过共享事件契约 11 个测试、API analytics/admin/cycles 95 个测试、匹配页与后台 Storybook 30 个浏览器测试，覆盖手机及桌面复制埋点、敏感值排除和后台统计说明。真实 PostgreSQL 回归已加入 `apps/api/test/autumn-match-lifecycle.e2e-spec.ts`，覆盖并发揭晓、outbox 失败回滚、补偿幂等和历史手动引荐排除；执行结果以本次四项修复总验收记录为准。
