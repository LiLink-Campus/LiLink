# 环境重建、数据迁移与域名割接

> 文档归属：[操作指南](README.md)。

本指南用于已获授权的环境迁移。执行前单独确认源/目标身份、数据处理范围、停写窗口、恢复与下线授权；指南本身不授权操作真实生产数据。连接与资产标识由受控配置提供，公开记录只使用源环境、目标环境等角色。当前部署契约见 [系统拓扑](../reference/topology.md)，资产归属与尚待确认的选择见 [迁移计划](../plans/environment-migration.md)。

## 建立范围和责任

1. 确定是换主机、数据库、Web 项目、邮件渠道、资产归属，还是其中一部分；列明负责人与获授权执行人、可接受停机/数据损失、割接窗口和停止判据。
2. 从当前运行环境核对 API/Web SHA、migration 历史、源数据库、DNS/边缘规则、实际配置来源、备份恢复能力和后台写入者。不得用旧交接快照代替身份核验。
3. 接收方建立自己控制的云、数据库、Web、邮件与监控项目，邀请可撤销的成员角色。原环境仅提供授权的代码历史、域名转移能力、必要数据和配置项清单，不移交个人账户密码或个人 SSH 私钥。
4. 分别记录域名/注册商、DNS、主机、数据库、Web、邮件、监控的负责人、权限与恢复渠道；验证 MFA、救援入口、账单/续费与告警接收。迁移前先确认目标可独立运维。

## 配置与密钥处理

按 [配置校验](../../apps/api/src/config/env.ts)、[API 配置样例](../../apps/api/.env.example)、[Web 配置样例](../../apps/web/.env.example) 和部署来源列出完整清单；值仅写入受控 secret 存储。不要将旧环境文件整体复制到仓库。

| 处理 | 核对内容 |
| --- | --- |
| 保持对外契约或明确变更 | Web/API origin、`/v1` 路径、CORS、cookie 名称/作用域、HTTPS、邮件发件域及用户可见链接 |
| 新目标重新签发 | 数据库连接与 role、主机/CI 部署权限、SMTP 凭据、监控上传 token、`JWT_SECRET`、`ADMIN_JWT_SECRET`、`MERCHANT_JWT_SECRET`、`CRON_SECRET`、`REDEEM_TICKET_SECRET` 和维护绕过密钥 |
| 由新服务产生并核验 | 数据库 endpoint、监控 DSN、项目/部署标识、邮件发件身份；它们不是随机生成的密钥，也不沿用旧个人项目 |
| 保留业务数据 | 用户/商户/管理员密码 hash、历史业务标识、关系与 migration 历史；另行审查旧操作者是否继续有权访问 |

更换各角色的 JWT 签名密钥会使对应旧会话失效，应通知重新登录并验证新的 cookie 边界。用户 `JWT_SECRET` 也用于 [邮箱验证码 HMAC](../../apps/api/src/modules/auth/auth.service.ts)，轮换后未过期且未消费的旧验证码同样失效；按授权处置旧验证码邮件并要求重新获取，不能恢复 outbox 后直接重发旧码。管理员 bootstrap 不重置已有邮箱的密码；按 [生产发布](production-release.md#容器内检查) 建立接收方访问，再有序撤销旧操作者。核销签名或其他密钥更换前审查尚有效票据及运行中的调用方，不能只改 API 而遗漏消费端。

## 预部署目标环境

1. 固定候选提交、兼容 API/Web 版本及工具链；保留源环境可恢复镜像和 Web deployment，并按 [发布前准备](production-release.md#发布前准备) 保存相应受控配置恢复点、核验恢复权限。先完成 [浏览器 E2E](browser-e2e.md) 与适用的 [隔离发布演练](release-rehearsal.md)。
2. 建立个人 SSH 访问、最小权限、救援控制台、TLS 代理和安全组。API 按 Compose 绑定 loopback；Web 服务端直连路径如启用，也需纳入网络策略。检验实际加载的代理配置，不假设历史主机目录仍正确。
3. 准备 runtime `api_env` 与独立 BuildKit secret，核对外部数据库 TLS/role、SMTP 和监控项目。检查日志保留、磁盘限额、外部探针、告警接收与数据库备份/PITR；为目标做恢复演练。
4. 在隔离目标恢复演练数据并记录精确版本；受控验收期间关闭后台任务和真实送信，避免演练轮次、旧邮件或重复任务触达真实用户。
5. 用临时受控 origin 或保留正式 Host/SNI 的访问验证 Web/API、TLS、CORS、登录与业务链路。临时域名 cookie 与正式域名不同，需要割接后重新验证，不能只看页面可打开。

生产入口会自动运行 migrations 和 bootstrap。恢复生产备份的目标不得先由应用创建业务 schema；先确定空目标与恢复顺序，保留备份中的 migration 历史，再由已选候选执行需要的迁移。生产副本进入目标后，访问与日志继续按真实数据权限管控。

## 数据迁移演练

1. 核验源库和隔离恢复目标的身份，明确导出范围、PostgreSQL 工具/服务版本、所需扩展、role 与权限；选择一致性导出和恢复方式，避免复制 provider 的内部角色或覆盖未知目标。
2. 完整导出业务数据、约束、索引和 migration 历史；备份加密、校验摘要、限定读者和保留期限，解密材料通过另一受控渠道提供。不得放入仓库或公开工件。
3. 在明确空且获授权的隔离数据库恢复。记录导出/恢复起止与错误，检查表和关键记录数量、关系/约束、索引、migration 状态与数据时点。完整 SQL 成功不能证明业务完整。
4. 在隔离环境验证管理员、用户和商户登录、问卷/报名、历史结果、权益、优惠券/核销及邮件队列处理；验收使用合成账户或经授权的数据，公开证据仅保留脱敏断言。
5. 演练实际恢复时间、候选迁移和回滚，确认窗口足够。无法恢复、关系断裂、版本不兼容或无法建立单写边界时，不进入正式割接。

[本地备份脚本](../../scripts/backup-postgres.sh) 针对本地 Docker PostgreSQL，不是外部生产库的迁移入口。[专项 database 工具](../../scripts/release/database.mjs) 固定隔离目标且包含破坏性恢复，不能改连接后当作通用生产恢复脚本；只按 [演练指南](release-rehearsal.md) 的边界使用。

## 邮件与观测迁移

接收方在自己的邮件账户验证发件域与所需 DNS，核对 SPF、DKIM、DMARC、发件人和退订链接；变更前保存旧 DNS 规则以便恢复。受控测试应证明实际入箱与域认证，SMTP 接收日志不等于收件结果。

列明队列中待发、进行中、已发送和终态失败任务的处理规则；冻结前先处理活动投递，恢复后只启用一个发送者。服务商已接收但数据库未记为 `SENT` 的任务可能重试，应结合投递记录审查，不能仅靠唯一发送者保证不重复。避免旧库队列和新库队列同时送信；过期验证码和时效通知不能未经审查整批重发。

在新监控项目配置 release、source maps、告警和可撤销的成员权限，验证接收方实际收到告警。历史日志和用户内容按必要范围、保留期限与访问权限另行处理，不作为代码交付附件。

## 正式割接窗口

1. 固定代码与配置，确认接收方验收通过、恢复资源可用、用户已获通知；记录源/目标角色、实际提交、开始时间、DNS 规则与回退判据。
2. 建立停写边界：检查用户/API、管理员/商户、轮次/邮件后台任务、外部 cron、脚本、其他容器和进行中的事务。维护模式与 jobs 开关见 [生产发布](production-release.md#维护窗口与后台任务)，受控绕过请求仍可能写入。最终导出前停止或隔离全部源写入者，确认没有活动写入；只屏蔽 POST 或展示维护页不足以证明停写。
3. 在源停写后做最终一致性导出、加密传输与目标恢复，记录摘要和数据截止时间；再次核对 migration 历史、完整性与演练断言。源保持停写，目标在验收期间仅放行受控访问。
4. 启动选定的目标 API/Web，完成 candidate migrations 和账户访问核验；保持后台任务与邮件发送关闭，避免恢复数据立即触发旧任务。若使用维护绕过做必要写入，要记录这些增量，因为它们会影响回退条件。
5. 更新已核验的 DNS/边缘/Web 路由，保留旧规则；核对正式 origin 的 TLS、CORS、cookie、实际 SHA、数据库读取及用户页面。DNS 缓存可能仍将部分请求送至源，源应保持停写或按计划返回维护响应。
6. 由获授权执行人按计划开放目标业务写入，再启用唯一的后台任务与邮件发送者；检查重试、轮次/队列和缓存刷新，验证用户主链路。
7. 记录目标首次写入时间、验收、错误/延迟与业务状态；在约定观察窗口内保留停写源、加密备份与恢复入口。

## 回退与旧资源下线

目标未产生增量写入且旧源保持完整时，可以按已演练方案恢复旧路由与兼容版本；切回后只开放旧源写入。目标已有新数据时先冻结目标，核验新增/变更数据与邮件等外部副作用，制定增量归并或受控恢复方案；直接切回旧库会丢数据。镜像回滚不能自动撤销数据库迁移。

回退和恢复按 [生产发布](production-release.md#回滚) 执行并重新验证用户状态。不能证明数据一致与单写边界时保持维护窗口，不同时开放两边以等待观察。

只有接收方确认验收、备份恢复、账单/续费、权限、告警、数据保留期限和观察窗口完成后，才按单独授权下线旧资源。先撤销旧部署与数据库/邮件权限，再删除获授权对象；明确 DNS 缓存、旧队列、备份和旧个人账户资产的处置。记录角色、对象类型、时间、结果和遗留事项，公开记录不包含真实资源标识。

## 验收与交付证据

交付记录应包含命令与工具版本、环境/数据前提、API/Web SHA、停写与首次新写入时点、迁移与恢复断言、用户链路结果、邮件/任务唯一执行者、回退条件及未验证项。备份、密钥、私有连接配置、内部资源标识、真实统计与原始日志留在受控位置；公开工件只保存可重复的脱敏验收方法和结果。
