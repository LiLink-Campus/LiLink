# 值守与故障排查

> 文档归属：[操作指南](README.md)。

## 检查主链路

1. 确认目标环境与时间窗口，记录用户症状、API/Web SHA 和错误范围，保留脱敏请求关联信息。
2. Web 无法打开时检查 deployment、路由与域名；API 失败时检查进程、Compose、反向代理与 `health`。
3. `health` 正常而业务失败时检查数据库与 migrations，并对受影响接口定位认证、授权和请求日志；`landing` 有缓存，不能单独证明当前数据库可用。
4. Web 服务端与浏览器表现不一致时核对 [API 路由](../reference/server-api-routing.md) 和 [公开缓存](../reference/public-data-cache.md)，区分源站、边缘路径与缓存。
5. 邮件失败时检查 outbox、SMTP 配置和送达证据。SMTP accepted 不能单独证明真实收件。
6. 轮次失败时检查状态、截止/揭晓边界与后台预演，按 [匹配参考](../reference/matching.md) 核对资格和数据时点。

## 值守准备与日常巡检

由当值人维护受控的资产与联系人清单：主机/控制台、DNS、Web 项目、数据库备份、邮件、监控、续费与告警。确认实际版本和环境角色，不使用历史 IP、项目标识或旧容量统计判断现场。新维护人应亲自验证访问、告警接收与恢复入口；共享个人密码不能代替可撤销的成员权限。

在已核验的 Linux 主机进行只读检查，可分别运行：

```sh
date -u
uptime
df -h
free -h
docker ps
docker stats --no-stream lilink-api
systemctl status docker --no-pager
systemctl status caddy --no-pager
```

检查公网与 loopback 探针、容器重启次数、内存/磁盘趋势、错误窗口与请求延迟。Docker 和 journal 的保留策略、备份/PITR 与外部告警需现场确认，Compose 文件不证明这些保障已配置。日志仅取与症状相关的时间窗口，原始日志保留在受控位置；公开工件不包含凭据、私有连接配置、内部资源标识、真实邮件地址、业务统计或用户内容。

对数据库观察连接失败、耗时和恢复能力；对邮件观察待发送量、最老待发送时间、重试与终态失败；对轮次观察当前状态、报名截止和揭晓是否按计划推进。健康检查或旧历史失败总数都不能单独判定服务正常或当前事故。

## Web 无法打开，API 正常

1. 区分 DNS/TLS、边缘错误、Web deployment 未就绪和页面运行时错误。确认用户实际访问 origin、发生时间与当前 Web deployment。
2. 若浏览器与 Web 服务端表现不同，按 [服务端 API 路由](../reference/server-api-routing.md) 检查 base URL 和可选连接地址，按 [公开数据缓存](../reference/public-data-cache.md) 核对缓存来源；不要仅凭一次命中缓存认定源站已恢复。
3. 对比部署日志、页面错误和 release，核对 Web/API 是否混用不兼容版本。必要时按发布指南恢复兼容 deployment，并验证用户看到的页面与登录后状态。

## API 公网超时或代理错误

1. 对比公网 health、主机 loopback health 与容器状态。loopback 失败先看启动链、容器退出和资源；loopback 成功再看反向代理、TLS、DNS、边缘和防火墙。
2. 查 Caddy 实际 systemd unit、启动参数和加载的配置路径，不能默认它使用某个传统目录。对源站 HTTPS 的比较保留配置域名、Host、SNI 与证书校验，不使用关闭校验的成功结果替代用户路径。
3. 检查最近的部署、证书或网络策略变更。Web 若配置直连源站，防火墙也必须允许已确认的服务端路径；仅允许边缘来源可能同时切断 Web 服务端请求。
4. 恢复前确认远程控制台或救援入口可用。[防火墙脚本](../../scripts/firewall/cf-firewall-dryrun.sh) 名称含 dryrun，但会应用规则并依赖 watchdog 回滚；不能把它当作无副作用诊断命令。

## health 正常，业务接口失败

1. health 只证明进程响应。核对当前数据库角色、连接与 migrations；使用 [发布指南的容器入口](production-release.md#容器内检查) 加载受控配置后检查迁移状态，避免空 exec shell 给出错误结论。
2. 用脱敏关联信息检查受影响接口，区分认证/权限、数据库连接或耗尽、迁移不一致与业务异常。记录错误类型与时段，不把完整数据库 URL、查询结果或响应体复制到记录。
3. 连接资源异常时对照 [数据库连接配置](../../apps/api/src/common/prisma/client.ts) 与部署副本数、provider 限额、长事务及请求并发。先找占用和失败原因，调大连接池可能放大问题。
4. 恢复后验证具体用户行为和读取结果；landing 的旧缓存或单次成功不作为终验依据。

## 验证码或业务邮件未到达

1. 确认症状是任务未创建、未投递、服务商拒绝，还是服务商已接收但未入箱；记录脱敏时间与请求关联信息。
2. 检查 outbox 状态及更新时间：`PENDING`、`PROCESSING`、`FAILED`、`EXHAUSTED`，并核对重试时间和最近失败原因。历史队列总数不能代替当前积压年龄与趋势。
3. 按 [邮件服务](../../apps/api/src/common/mail/mail.service.ts) 检查维护、后台任务与送信开关；配置变化需核对实际运行进程。再检查 SMTP 主机、端口、TLS、发件域、配额和 DNS 验证，连接值只在受控配置中查看。
4. 恢复送信或迁移邮件账号前先核对已发送记录、进行中的任务及重试，避免重复通知或旧验证码集中发送。是否取消过期任务要有明确业务规则与授权。
5. 以受控测试收件人验证实际收件与发件域认证，必要时查垃圾邮件和服务商投递日志。SMTP accepted 不能单独证明邮件送达；真实生产送信需明确授权。

## 轮次截止或揭晓未推进

1. 在管理界面核对目标学校、轮次、状态、时间和时区，再核对预演的资格与数据时点。自动任务的运行和自动创建轮次不能从旧学期截图推断。
2. 对照 [匹配参考](../reference/matching.md) 与 [自动任务](../../apps/api/src/modules/cycles/cycles-automation.service.ts)，检查 jobs/维护开关、容器运行窗口和任务错误；任务按调度边界处理，不要求截止后立即完成。
3. 对 `PREPARING` 区分已经持久化结果与无结果的过期准备占用，查失败原因、是否仍有活动任务及恢复条件。恢复按 [cycles.service.ts](../../apps/api/src/modules/cycles/cycles.service.ts) 的状态校验执行，不因等待较久就反复强制匹配。
4. `force` 在 `OPEN` 轮次上会绕过相应时间窗口；非 `OPEN` 且非 `DRAFT` 的轮次先进入 reset 路径，删除已有 Match 和用户轮次 dashboard 快照；`DRAFT` 拒绝执行。先核对是否已揭晓、邮件和用户是否已看到结果，取得影响范围对应的授权并留存前态。不能把 `force` 当作日常巡检操作。
5. 恢复后验证轮次终态、用户首页/结果、引荐与邮件；同时确认没有重复揭晓或送信。

## 新学期或学校变更前

核对当前学校配置、问卷版本、轮次自动化和运营计划。先在隔离环境预演报名、资格、截止、揭晓与收件，再确认生产管理员可见状态；修改配置、手工建轮次或补历史数据分别授权。问卷升级可能影响已报名用户资格，学校变化也需要重新验证硬条件、时区与页面内容，不能复用旧用户数量或旧轮次清单作为验收。

## 恢复与记录

按 [生产发布与回滚](production-release.md) 选择已授权的恢复操作。数据库写入、服务重启与切流分别评估影响；保留前后状态和单写边界。

关闭故障前验证受影响的用户行为已经恢复，记录触发条件、影响、诊断依据、恢复操作和后续任务；私有日志与真实数据保留在受控位置。

把尚未解决的风险转为有负责人、证据和退出条件的任务；旧稿中关于日志轮转、探针、备份、账号归属或维护窗口的缺口需重新核验，不能原样标成现行缺陷。资产与数据库迁移另见 [环境重建与迁移](environment-migration.md)。
