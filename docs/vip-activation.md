## 上线顺序

1. 等库存读取恢复，导出商品 41665 的全部 10 张卡密，必须选择「不删除」。核对导出数量及没有重复码。
2. 将导出文件保存在 Git 忽略的私有目录，如 `.agent-local/vip/cards.txt`，每行一个 24 位卡密。不要提交、截图或在日志中展示明文。
3. 在仓库根目录生成摘要清单（已有目标文件时会拒绝覆盖）：

   ```sh
   node apps/api/scripts/vip-manifest.mjs .agent-local/vip/cards.txt .agent-local/vip/manifest.json catfk-41665-20260917
   ```

4. 取得部署授权后，按现行生产运维流程部署前后端及 `20260917080000_vip_activation` 迁移。先在隔离测试环境用合成卡密验证，不能消耗待售卡密。
5. 在正确的受控运行环境内使用已有数据库凭据，先预览目标主机、库名和数量，再导入；脚本不会输出数据库密码。不要另开一个没有生产 secret 的 `docker exec` shell 并假设它会继承数据库变量。

   ```sh
   node apps/api/scripts/vip-codes.mjs import .agent-local/vip/manifest.json
   node apps/api/scripts/vip-codes.mjs import .agent-local/vip/manifest.json --apply
   ```

   路径按实际受控环境调整；API 必须已构建。重复导入跳过既有码，不会恢复已停用卡密。

6. 确认正式站登录、会员查询和兑换入口正常、所有待售卡密摘要已入库；云猫审核通过后上架，更新商品说明中的联调提示，并检查买家端价格、数量、查单密码和支付渠道。
7. 用户亲自完成一笔真实付款，再从订单取码、在目标账号激活、刷新核对到期时间、在另一账号验证不可重复兑换。核对云猫订单与收款记录后再对外推广。

## 退款与停用

先核对订单与绑定账号，用该订单对应的单个码生成单码摘要清单，不要误用整批清单。对未兑换或已兑换卡密均可停用；停用已兑换卡时移除该卡尚未使用的时长，后续续费卡相应提前，保留其他卡完整的剩余权益。已经用完的卡不会重复扣除其他卡的时长，重复执行停用也不会重复扣减。随后由有权限的运营处理平台退款并留存订单记录。

例如 A、B 两张卡共 60 天：第 10 天停用 A，A 剩余的 20 天被移除，B 从此时提供完整 30 天；若停用的是尚未开始的 B，则 A 的到期日不变。停用与激活按账号串行处理，归属在并发兑换中改变时会重新取得锁后重试。必须使用下方 CLI，不要仅在数据库写 `revokedAt`，否则后续卡的累计时长不会同步更新。

```sh
node apps/api/scripts/vip-codes.mjs revoke .agent-local/vip/refund-one.json
node apps/api/scripts/vip-codes.mjs revoke .agent-local/vip/refund-one.json --apply
```
