# 注册信息最小化与昵称后置

决策日期：2026-09-10。适用于学校邮箱与普通邮箱两种注册路径。

## 决策

**真实姓名不再收集；昵称在注册或登录成功后，由用户在资料／名片中填写。** 注册只负责建立可登录的账号，不要求用户同时完成对外展示资料。

| 信息 | 注册时 | 登录后 | 存储与用途 |
| --- | --- | --- | --- |
| 真实姓名 | 不展示、不提交、不接收 | 不新增收集入口 | 不再写入新姓名；历史数据另行处理 |
| 昵称 | 不展示、不提交，不作为注册条件 | 在「匹配资料」或「我的 → 编辑名片」设置 | 用于匹配对象展示；由用户主动填写后存储 |
| 邮箱、验证码 | 同屏完成邮箱信息填写 | 继续按现有账号机制使用 | 邮箱用于账号联系与验证，验证码由后端校验 |
| 密码 | 设置并确认 | 按现有找回／修改机制处理 | 沿用后端密码哈希机制 |
| 学校与邀请码 | 学校邮箱按现有规则识别；普通邮箱需要邀请码及学校选择 | 按现有规则维护 | 支持学校归属和邀请资格，不替代实名验证 |

## 为什么这样调整

1. **区分身份验证和自我介绍。** 邮箱验证用于确认账号联系渠道；昵称是用户希望怎样被认识。两者不必在同一时间完成，真实姓名也不是当前校园匹配流程的必要注册输入。
2. **减少注册前的填写与决策负担。** 用户先完成账号建立，再在明确用途的资料页决定昵称。预计这能让注册更直接，但本次没有转化率实验，不能把这一预期写成已验证的提升。
3. **减少非必要身份信息。** 不以真实姓名作为昵称要求，不把它改名为其他字段继续收集。昵称是展示名，不表示经过实名核验。
4. **降低用户对资料去向的疑惑。** 在名片页填写昵称时，用户能看到它将怎样展示给匹配对象，比在注册表单里孤立地填写更容易理解。

## 用户流程

选择注册方式 → 填写邮箱和验证码 → 设置密码（普通邮箱另选学校）→ 注册成功并进入登录态 → 按需要完善匹配资料／名片并设置昵称。

已有账号登录后同样使用资料／名片入口。此次不新增强制昵称弹窗，不增加注册前置步骤；原有资料完整度与匹配参与规则继续保留。能登录、能浏览页面不等于已经完成匹配资料。

未设置昵称时，数据库 `User.displayName` 保持 `null`。页面可以显示「同学」「未命名同学」等占位文案，但不把占位文案、邮箱前缀或随机名字写成用户昵称。已有昵称继续保留，登录时不清空、不重复索取。

## 实现与边界

- 原站与视觉副本的两种注册表单均移除昵称、真实姓名状态与提交字段。
- 注册 DTO 不再接受 `displayName` 和 `fullName`；携带这些字段的请求被现有白名单校验拒绝。注册服务明确以空昵称创建账号，不写入真实姓名。
- 登录后的昵称更新入口和现有昵称校验继续保留。资料更新 DTO 不再接受真实姓名。
- 真实姓名的历史数据库列、已有记录和后台只读历史展示暂时保留。本决策不授权直接删除历史数据；清理范围、处理方式及相关说明需单独确认。
- 视觉预览使用虚拟资料，预览里已有示例昵称不代表注册时采集，也不能作为真实业务完成的证据。
- 改动已落实到本地源码，尚未提交或部署。上线需协调前后端版本，因为旧客户端继续提交注册昵称／真实姓名会被拒绝。

## 验收

- 两种注册页面均无真实姓名、昵称输入框，账号设置文案说明昵称可在登录后填写。
- 不带姓名／昵称的注册请求通过 HTTP 参数校验；返回会话时可携带 `displayName: null`。
- 注册服务创建数据中的昵称为空；注册时提交昵称或真实姓名被拒绝。
- 登录后提交合法昵称仍可通过资料接口校验，真实姓名更新请求被拒绝。
- 保留已有注册校验：验证码、密码要求、协议确认及原有防刷限制。

本次验证：API、原站 Web、视觉副本类型检查通过；46 项服务／DTO 测试、10 项 HTTP 注册参数与会话响应测试通过。HTTP 测试使用模拟 AuthService，并非真实邮箱发信或生产注册验收。浏览器另核对两种注册账号设置页与登录后昵称入口。
