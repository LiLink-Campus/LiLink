## 一、一分钟快速看懂：这份报告在说什么？

团队在 `codex/autumn-2026-ui-implementation` 分支上完成了秋季新版视觉重构与关键业务改造（包括报名机制升级、揭晓时直接展示联系方式、支持软注销释放原邮箱等），共修改/新增了 212 个文件。

常规的自动化检查（编译构建、代码格式、611 项后端单测、84 项前端单测、26 项真实数据库 E2E 测试、157 项 Storybook 浏览器测试）**全部通过了**。

但是，审计人员通过**模拟真实并发交错、调用旧接口、制造极限时序**等反例测试，抓出了 **8 个常规测试覆盖不到的漏洞**：
- **3 个 P1 漏洞（致命）**：涉及**用户注销（软注销）后的隐私泄露**。用户以为自己已经成功注销了，但由于系统在并发缓存、旧接口、邮件队列中的漏洞，注销者的邮箱、微信、手机号仍然会被查到或发送给匹配对象。
- **4 个 P2 漏洞（严重）**：涉及**名额计算、管理后台操作、高校白名单展示、联系方式表单保存**。比如注销后名额没有被预检释放、输入错误手机号后换成邮箱也无法保存等。
- **1 个 P3 漏洞（轻微）**：新注册用户一进资料页就显示“草稿已自动保存”，属于误导性文案。

**审查结论**：建议**必须先修复 3 个 P1 和 4 个 P2 问题**，才能将代码合并入主分支 `main` 并上线。

## 二、为什么自动化测试全绿，还会藏着 8 个问题？

很多团队会困惑：“既然 600 多项单测和端到端测试都过了，为什么还会漏掉这些问题？”

| 测试类型 | 常规自动化测试做的事情 | 审查员抓出问题的方式 |
| :--- | :--- | :--- |
| **测试场景** | “正常单线流程”（A 注册 -> A 注销 -> 检查 A 状态为已注销） | **“极端交错并发”**（任务 1 刚读到 A 未注销，A 突然注销，任务 1 随后把旧数据写回） |
| **接口范围** | 测试当下新 UI 所用的最新 API | **测试系统没删干净的历史旧 API**（新 UI 不点了，但不代表恶意调用或脚本调不到） |
| **异步队列** | 只要任务进入队列、Mock 显示成功就认为通过 | **追踪队列中间状态**（任务处于 PROCESSING 处理中时用户点注销） |
| **前端交互** | 验证各组件正常输入能触发保存 | **验证边界输入**（输入错误手机号后放弃，切换到邮箱，看隐藏的脏数据是否仍在破坏提交） |

常规测试保证了“主干链路在平稳运行时是通的”，而深度审查发现了“高并发、时序差和边界角落里的定时炸弹”。

## 三、8 处问题逐项通俗大白话拆解

---

### P1 级（阻断合并·重大隐私安全风险）

#### 1. 敏感缓存“死灰复燃”：注销后个人信息被旧任务刷回
- **涉及代码**：`apps/api/src/common/dashboard/dashboard-snapshot.service.ts`、`apps/api/src/modules/account/account-deletion.service.ts`
- **现实场景**：
  1. 系统后台有个定时或被动任务正在“刷新匹配看板缓存”。它先查了一下数据库，发现小明是正常用户（此时读出了小明的原邮箱和真实资料）。
  2. 恰在此时，小明在前端点击了“注销账号”。注销事务飞速执行完毕，把小明标记为已注销（LIMITED），清空并隐藏敏感信息。
  3. 但刚才第 1 步的那个后台任务刚缓过神来，把手里先前读到的旧资料执行了一次 `upsert`（无条件写入/更新缓存）。
  4. 结果：小明的已注销保护被覆盖掉了！匹配给小明的对方用户打开主页，居然依然能清清楚楚看到小明注销前的真实邮箱和资料。
- **核心原因**：快照更新任务在读取数据到写入数据之间存在时间差，且写入时没有校验“这期间用户是否已注销”，直接用旧数据盲目覆盖了注销写入的安全状态。
- **修复方案**：
  - 写入快照前增加乐观锁/版本比对条件；或者与注销事务获取一致的锁。
  - 在返回看板数据给前端时，增加一层实时的“注销状态快速核对”兜底，绝不单纯信任静态缓存。

---

#### 2. 历史遗留接口成了“隐私后门”：注销后仍可索要联系方式
- **涉及代码**：`apps/api/src/modules/account/account.controller.ts` (`POST /me/matches/:matchId/contact`)、`apps/api/src/modules/account/account.service.ts`
- **现实场景**：
  1. 在秋季新版中，匹配揭晓后直接展示联系方式，旧版的“手动点击索要联系方式”接口（`POST /me/matches/:matchId/contact`）在新前端已经没有入口了。
  2. 但后端的这个旧接口没有下线！
  3. 如果小红和小明是历史匹配对象，小明现在已经注销了账号。因为项目采取“软注销”（保留部分历史以防纠纷），数据库里还存有小明的微信号。
  4. 小红通过接口直接发请求索要联系方式，该接口检查了是否揭晓、是否被拉黑，**唯独忘记检查“对方是不是已经注销”**。
  5. 结果：系统大方地把已注销用户小明的私人微信重新打包成引荐邮件，发给了小红！
- **核心原因**：废弃的历史入口没有关闭，且业务校验缺少 `deactivatedAt == null`。
- **修复方案**：
  - 如果该接口彻底不再需要，直接下线并移除路由。
  - 若需保留，必须在加锁事务中严格校验对方用户的激活状态（已注销直接抛 400 拦截）。

---

#### 3. 队列中的待发邮件“刹不住车”：注销后依然发送联系方式
- **涉及代码**：`apps/api/src/modules/account/account-deletion.service.ts`、`apps/api/src/common/mail/mail.service.ts`
- **现实场景**：
  1. 系统刚揭晓了一批匹配，准备给双方发邮件通知对方的微信号。
  2. 邮件发送系统是批处理的：系统把这批邮件从“等待中（PENDING）”变成了“正在处理中（PROCESSING）”，然后排队等待发信通道（SMTP 连接池限制）。
  3. 就在这几秒排队等待的间隙，小明果断申请注销了账号。
  4. 注销逻辑很负责地去数据库取消邮件，但它的代码写的是：`取消所有状态为 PENDING 或 FAILED 的邮件`。
  5. **它漏掉了 `PROCESSING`！** 导致已经在排队的这封包含小明微信号的邮件不受影响，依然被 SMTP 正常发了出去。
- **核心原因**：注销清理逻辑没有把“已领单但还没真正打给 SMTP”的中间状态（`PROCESSING`）拦截下来，并且邮件发送器在调用 SMTP 发送前没有做二次注销核验。
- **修复方案**：
  - 在注销时，把 `PROCESSING` 状态也纳入取消范围（标记为作废）。
  - 在 `MailService` 真正调起 `sendMail` 的最后一毫秒，快速再查一下该邮件是否被取消或用户是否已注销，若已取消则直接丢弃不发。

### P2 级（阻断合并·业务逻辑与体验阻塞）

#### 4. 注册预检“占着名额不放”：注销腾出的名额新用户用不了
- **涉及代码**：`apps/api/src/modules/auth/auth.service.ts`
- **现实场景**：
  1. 系统设置了注册人数上限（比如限制 500 人）。
  2. 陆陆续续有 500 人注册过，但其中有 100 人注销了，当前有效活跃用户只有 400 人，理应还可以再进 100 人。
  3. 用户提交注册时，代码里有两道关卡：第一道是先跑一个“快速预检（Preflight）”，第二道才是“数据库入库事务”。
  4. 在第二道事务里，代码正确过滤了注销账号（`where: { deactivatedAt: null }`）；
  5. **但在第一道预检里，开发人员顺手写成了 `user.count()`（统计了全表所有账号，包括注销的！）**。
  6. 结果：预检一算“历史总数 500 >= 上限 500”，直接在门外报错“名额已满”，注销腾出的名额谁也进不去，原邮箱想重新注册也被挡在大门外。
- **核心原因**：预检逻辑与最终事务校验逻辑的过滤条件不一致。
- **修复方案**：将预检中的 `user.count()` 统一加上 `{ where: { deactivatedAt: null } }`。

---

#### 5. 管理后台并发保存导致注销用户“被动复活”并抢占原邮箱
- **涉及代码**：`apps/api/src/modules/admin/admin.service.ts`
- **现实场景**：
  1. 管理员在后台打开了用户小李的资料编辑弹窗（此时读到小李的状态是正常 ACTIVE，邮箱是 `li@school.edu.cn`）。
  2. 此时小李在前台自助注销了账号。注销程序把小李状态改成 SUSPENDED，邮箱改成废弃后缀 `deactivated-xxx@accounts.invalid`，从而把 `li@school.edu.cn` 释放出来供重新注册。
  3. 随后管理员在后台点击“保存”。后台更新接口由于是在事务外查的状态，直接用先前读到的表单数据执行了更新。
  4. 结果：小李的邮箱被强行写回 `li@school.edu.cn`，状态写回 ACTIVE！小李被“僵尸复活”，原本释放的学校邮箱又被占死了。
- **核心原因**：管理后台在保存时没有防并发覆盖，更新语句没有限定条件 `deactivatedAt: null`。
- **修复方案**：
  - 更新时限定 `where: { id: userId, deactivatedAt: null }`。
  - 若受影响行数为 0，说明该用户已被注销，立刻终止并向管理员提示“该账号已注销，无法编辑”。

---

#### 6. 支持高校页面写死假数据，脱离后端真实开通名单
- **涉及代码**：`apps/web/src/app/schools/page.tsx`、`apps/web/src/app/schools/school-domain-directory.tsx`
- **现实场景**：
  1. 用户访问网站的 `/schools` 页面想查自己的学校能不能玩。
  2. 该页面下方的“学校邮箱后缀目录”，直接读取了前端写死的一份本地静态列表（`partners.ts`）。
  3. 导致：后端数据库里明明支持的学校（如华北电力 `ncepu.edu.cn`、长安大学 `chd.edu.cn` 等）在页面上找不到；而页面上展示的一些境外后缀，后端其实根本没开放。
  4. 结果：学生以为自己的学校不支持就走了，或者看到了自己的学校结果注册时报不支持。
- **核心原因**：前端展示与后端真实接口 `/v1/public/schools` 脱节。
- **修复方案**：合作办学介绍的图文保留，但邮箱后缀与支持名单必须通过 API 动态获取真实数据。

---

#### 7. 手机格式报错被吞，隐形错误还卡死其他联系方式
- **涉及代码**：`apps/web/src/app/dashboard/profile/contact-editor.tsx`
- **现实场景**：
  1. 用户在资料页填写手机号，国内用户习惯直接填 `13800138000`（没有填国际区号 `+86`）。
  2. 后端校验要求带区号，返回了明确的错误说明：“电话号码必须包含国际区号”。
  3. 但新前端组件在 `catch` 块里把错误丢弃了，只在屏幕上显示冷冰冰的一句：“联系方式保存失败，请重试”。用户完全不知道错在哪。
  4. 更严重的是：用户被搞烦了，心想“那我不用手机了，我改选邮箱吧”。
  5. 用户选中“邮箱”，点击保存。但组件在后台打包请求时，把刚才填的那个无效手机号草稿一起带了上去！
  6. 结果：后端依然校验到了那个隐藏的无效手机号并报错，导致选邮箱也存不上！用户彻底卡死。
- **核心原因**：前端吞掉了后端详细的 400 校验错误；并且没有在提交时清理非选中渠道的脏草稿。
- **修复方案**：
  - 把后端返回的具体错误原因展示给用户（如“请输入包含国际区号的号码，如 +86...”）。
  - 切换联系方式渠道时，或者提交时，非选中的无效草稿不应阻塞已选渠道的保存。

### P3 级（低优先级·文案与显示瑕疵）

#### 8. 新账号刚注册打开页面，就谎报“草稿已自动保存”
- **涉及代码**：`apps/web/src/app/dashboard/profile/profile-client.tsx`
- **现实场景**：
  - 一个刚注册的新用户第一次点进个人资料页，一个字都还没填，界面右上角就赫然显示一个绿色的状态徽章：“草稿已自动保存”。
  - 用户会感到困惑：“我明明还没填，系统替我保存了啥？”
- **核心原因**：前端代码判断“是否有草稿”时，写了一句 `hasQuestionnaireDraft || Boolean(questionnaireIncompleteMessage)`。因为新用户必填项都没填，`questionnaireIncompleteMessage` 必然为真，导致代码把“有必填项未填写”错误当成了“有草稿已保存”。
- **修复方案**：修正布尔表达式，只有当真正发起过保存并得到草稿回执时才显示“草稿已自动保存”，空白状态正常显示“尚未填写”。

## 四、修复优先级与实施清单

| 编号 | 级别 | 问题简述 | 影响模块 | 修复要点 |
| :---: | :---: | :--- | :--- | :--- |
| **1** | **P1** | 注销后快照可能被旧并发任务覆盖复活 | 后端看板服务 | 写入增加版本/注销排斥锁，输出增加注销状态校验兜底 |
| **2** | **P1** | 旧索要联系方式接口泄露注销用户联系方式 | 后端账号服务 | 移除无用旧路由，或在事务中强行校验对方 `deactivatedAt` |
| **3** | **P1** | 邮件队列中 `PROCESSING` 状态绕过注销取消 | 后端邮件服务 | 扩充取消状态，并在 SMTP 发送调用前最后核对取消状态 |
| **4** | **P2** | 注册名额预检错误计入已注销账号 | 后端认证服务 | 预检语句统一追加 `{ deactivatedAt: null }` 过滤 |
| **5** | **P2** | 管理后台并发保存覆盖注销并复活旧邮箱 | 后端管理服务 | 更新条件增加 `deactivatedAt: null`，防止篡改注销状态 |
| **6** | **P2** | 高校邮箱目录未接入真实后端白名单 | 前端学校页面 | 接入 `/v1/public/schools`，展示真实开通后缀 |
| **7** | **P2** | 联系方式报错被吞，无效草稿卡死有效选择 | 前端资料组件 | 抛出具体错误提示；过滤非选中渠道的非法脏数据 |
| **8** | **P3** | 新账号初始展示错误的草稿保存状态 | 前端资料组件 | 纠正布尔逻辑，仅依据真实保存事件展示“草稿已保存” |

### 建议后续执行顺序：
1. **第一阶段（解决安全与隐私漏洞）**：完成问题 1、2、3 修复，补充并发注入单测与集成测试；
2. **第二阶段（解决核心业务与数据一致性）**：完成问题 4、5、6、7 修复；
3. **第三阶段（体验收尾与合并）**：完成问题 8 修复，执行全量自动化回归；确认无误后再合并 `main`。
