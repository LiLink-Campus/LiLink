## 已确认的目标与范围

- 最新执行决定：删除此前全部 Demo，将当前 `apps/web` 原样复制到本目录的 `web/`，后续逐处微调。原样复刻阶段不实施下述导航、文案、视觉或流程建议；这些内容仅保留为讨论记录。

- 新生注册并参与匹配为优先设计场景，同时保证老用户回访时能快速理解当前状态。两者是同一产品的不同使用阶段，不是互斥目标。
- 对外核心定位已确认：优先帮助学生寻找恋爱对象，其次支持认识朋友。首页第一印象需要体现这一主次，不把两者做成等权入口。
- 用户明确暂不做多人局，原因是复杂度过高。首页移除多人局和“即将开放”预告，只保留 1v1 匹配，不再要求用户选择玩法。
- 用户进一步要求删除中间独立的 1v1 卡片，首页直接采用 CampusDate 的整页分区结构；参与入口放在首屏及页面结尾，仍沿用 LiLink 自身内容和素材。
- 预计以手机浏览器为主、电脑为辅。这是当前判断，尚未用设备访问数据验证。
- 当前最需要解决的是：用户不知道完整流程、不清楚下一步、不确定自己是否已报名。
- 用户希望改善 PWA 安装提醒，让用户更容易再次打开 LiLink。
- 本轮讨论和 Demo 放在本目录；先确认设计，再进入正式页面改造。
- 个人展示信息丰富化、表白墙和个人展示等属于未来功能，本轮不设计页面或预留可见入口。未来启动时重新评估导航与功能边界。
- Landing page 属于本轮范围，同时承担匹配产品介绍和官方社媒引流，当前主要渠道为小红书和微信私域。
- 关于我们页考虑介绍团队成员及职责，并提供成员个人社媒入口；这是本轮品牌展示需求，与未来用户个人展示功能分开。该页着重追求流畅、精致、有记忆点的视觉和交互。
- 素材方向已修正：无需由助手提供照片，团队主要考虑使用动漫形象或社媒头像。Demo 先保留头像占位，素材由用户后续提供。
- 最新导航决定：顶部保留“关于我们 / 支持的学校 / 登录”；常见问题、更新、注册等入口放在页脚。这替代此前顶部 FAQ 入口的方案。
- 最新常见问题决定：内容放在首页底部，与关于我们分开；页脚“常见问题”入口直接定位该区。对用户展示的 FAQ 措辞统一改为“常见问题”。

## 建议方向，尚待确认

### 用当前状态组织页面

每个阶段优先回答三个问题：我现在到哪一步了、下一步做什么、完成后会发生什么。

首次参与的说明主线可以写为：注册并验证 → 完善匹配资料 → 确认参与 → 等待揭晓。

这是面向用户的流程表达草案，不代表四个固定页面，也不改变现有参与规则。

| 用户所处情境 | 页面首先说明 | 主要行动 |
| --- | --- | --- |
| 尚未注册 | LiLink 能帮我做什么，参加需要经历哪些步骤 | 开始注册 |
| 已注册但资料未完成 | 尚缺哪些必要信息，之前填写的是否保留 | 继续完善 |
| 已具备参与条件但尚未参与 | 资料已就绪，本轮还未报名 | 确认参与本轮 |
| 已参与、等待揭晓 | 明确显示本轮已报名、揭晓时间和是否还需操作 | 无须强行制造待办；按当前规则提供查看或修改入口 |
| 已截止、未参与 | 本轮未报名且已截止，后续安排是什么 | 仅展示当前确实可用的后续行动 |
| 已揭晓 | 本轮实际结果，包括未匹配成功的情况 | 查看结果或后续说明 |

跨轮次沿用、自动暂停、资料更新等特殊情况须结合现行规则另行展开，不能统一假设为“每周必须重新报名”。

### 报名结果应持续可查

- 完成资料不等于报名成功；页面需要明确区分。
- 报名成功不能只依靠短暂提示，应在返回首页、刷新和再次进入后仍清楚可见。
- “已报名”不等于“必定匹配成功”，说明和结果状态需要区分。
- 提交中、提交失败、截止时提交等情况必须单独设计，不能误报成功。
- 报名状态必须以服务端确认的事实为准。

### PWA 提醒的讨论方向

- 候选时机：首次成功参与后，以不打断流程的方式提醒；常驻入口可放在个人页。
- 面向用户的候选文案：“添加到手机桌面，下次直接打开 LiLink”。
- 用户暂时跳过后避免反复打扰；频率、安装识别和各浏览器指引尚待设计与验证。
- 不把安装作为报名门槛，也不承诺安装后就能收到匹配通知。

### Landing page 与关于我们

以下是建议，尚未确认为最终结构：

- Landing page 依次回答：这里能帮我认识谁 → 如何参与 → 为什么可以信任 → 暂时不参加时如何继续关注。
- 恋爱匹配作为首要叙事，认识朋友作为补充说明；不承诺报名后一定获得对象或匹配结果。
- 首页主行动是开始参与；小红书和微信集中在页脚的“关注我们”区域，参考 CampusDate 与分组导航并排展示。具体账号和二维码由用户提供。
- 关于我们以创立缘由、团队成员和职责组织内容。团队人物展示与社媒入口相邻，区分 LiLink 官方渠道与成员个人账号。
- 团队展示候选方向：动漫形象或社媒头像配短介绍、疏密有序的排版、克制的滚动过渡；手机端重要信息和链接直接可见，不能依赖悬停才能发现。不再采用此前讨论的真人摄影方向。
- FAQ 放在首页底部的“常见问题”区域；注册条件、参与流程等决策所需信息仍应在对应操作附近解释，避免用户反复跳转。
- 顶部为 `关于我们 / 支持的学校 / 登录`；已登录时“登录”呈现“我的匹配”。页脚分为品牌、探索、支持、关于、关注我们；手机端纵向排列。首页通过 Logo 返回，注册入口保留在页脚和现有登录流程中。
- 官方小红书、微信私域具体承接方式和成员素材尚未提供；原型应明确标注占位内容，不使用虚构的真实账号或可扫描占位二维码。

## 当前源码核对

以下是源码观察，尚不代表已完成登录后的真实业务验收：

- `apps/web/src/app/dashboard/home-client.tsx`：参与动作会调用 `PUT /me/participation`，提交 `optIn: true` 和本周意向；退出则提交 `optIn: false`。成功提示目前着重表达“本周意向已锁定”。
- `apps/web/src/app/dashboard/_lib/progress.ts`：参与资格关联问卷提交、资料就绪和一句话介绍等条件。
- `apps/web/src/app/dashboard/_lib/agenda.ts`：已有“本周已参加”状态文案，后续应检查它的展示优先级和用户能否一眼发现，而不是假设当前完全没有状态提示。
- `apps/api/src/modules/cycles/cycles.service.ts`：存在跨轮次参与沿用逻辑的调用，完整规则须进一步核对。
- `apps/web/src/app/manifest.ts` 和 `apps/web/src/app/_components/ServiceWorkerRegistrar.tsx`：已有 PWA manifest 和生产环境 Service Worker 注册；开发环境跳过 Service Worker 注册。当前本地开发页面不能作为完整 PWA 安装验收依据。
