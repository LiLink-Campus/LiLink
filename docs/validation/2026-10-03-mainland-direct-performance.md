# 2026-10-03 大陆直连公开页面性能补测

> 文档归属：[验证记录](README.md)。用户关闭 TUN 后进行只读复测，已完成 72/72 次观察，前后浏览器出口均为 CN。全部样本达到内容就绪条件，52 次无告警、20 次有网络告警，状态为 `OBSERVED_WITH_ERRORS`。本页记录当前线上版本在这台设备、这条大陆出口网络下的表现，不代替尚未部署的 CDN 候选前后对照。

## 范围与前置证据

本轮目标是接近真实中国大陆用户的访问路径，因此直接使用实际网络，不叠加上一轮的 150 ms 延迟、10 Mbps 限速或 4 倍 CPU slowdown。使用匿名隔离 Chromium 148.0.7778.96，正常动画、桌面及移动视口。清除测试进程的代理环境变量，并在每个浏览器上下文显式配置全域代理绕过；仅使用 `--no-proxy-server` 在这台机器上不够。系统代理设置保持原样；移动视口仍运行于 Mac，不能称为真实 Android 或 iPhone。

上一轮[本地对照验收](2026-10-03-public-performance.md)得到的是实验室的源码差异和渲染性能。本轮只观察当前线上站点，未部署工作树变更，不输出“新 CDN 在大陆不退化”的结论。也不能直接用本轮真实网络的绝对耗时与上一轮 localhost 耗时计算改进比例。

`artifacts/performance/direct-network-20261003/` 保留脱敏证据：

- `initial-probe.json`：2026-10-03 15:06 UTC 清空代理变量并使用 `curl --noproxy '*'` 后，Cloudflare 返回 `country=CN`、`colo=LAX`。这是客户端出口地区与本次服务节点，并不说明 Cloudflare 静态 CDN 候选已上线，也不代表所有大陆运营商。另一测试域名 `one.one.one.one` 在 12 秒边界连接超时，保留失败，不把单一探测成功当作全部域名可达。
- `routes.json`：Web、API、Cloudflare 探测域名的真实 IPv4 解析均通过 `en0`，没有上轮的 fake-IP 或 `utun1024` 路由。IPv6 查询未得到路由，不能记为 IPv6 成功；macOS `route` 即使显示 `not in table` 也可能退出 0，因此依据实际接口字段判断。
- `site-preflight.json`：根域返回 307 到 `https://www.lilink.top/`；规范域首页返回 200，标题为 LiLink；`https://api.lilink.top/v1/health` 返回 200。单次 HTTP 成功仅证明预检可达，不等于页面完整可用。

系统 HTTP、HTTPS 和 SOCKS 代理仍启用。只在本轮 curl 和隔离浏览器进程内绕过，不修改全局配置。仅凭关闭 TUN 或看到 `en0` 不足以确定出口，本轮同时记录外部地区探测；不保存用户出口 IP、Cookie、认证头或真实账户数据。

## 浏览器代理校验

初次 `browser-observation/` 使用清空代理变量和 `--no-proxy-server`，浏览器实际探测仍为 SG/SIN。发现后停止，保留 8/72 条记录，状态为 `INCOMPLETE`，**不纳入大陆结果**。同一时段 curl 仍为 CN/LAX，说明 curl 的出口不能代替浏览器的出口证据。

`chromium-proxy-diagnostic.json` 核对了真实 Chromium 进程的启动参数和代理变量；`chromium-trace-transport.json` 进一步证实浏览器连接了本地代理端口 7897。该响应时间戳是实时的，使用 IPv4/h2，未命中磁盘缓存或 Service Worker，因此不能归因于旧探测响应或 IPv6 路径。

`context-proxy-bypass-diagnostic.json` 记录修正后的独立上下文：`proxy: { server: 'http://127.0.0.1:9', bypass: '*' }`。其中端口 9 是不使用的占位代理，`bypass: '*'` 让所有目的地直连；没有启动新代理。实际浏览器探测转为 CN/LAX、目的端口 443。正式重测使用全新目录 `browser-observation-direct-v2/`，前置探测必须同时满足 CN、443 和非缓存才开始采样；结束再次核对。该设置仅作用于测试浏览器。

## 预先固定的采样边界

计划 3 轮：5 条公开路由 × 桌面/移动 × 冷/暖，共 60 次文档访问；首页进入关于页及注册页 × 两视口，共 12 次点击路径。浏览器串行采样，不与构建或其他浏览器压测并发。

冷访问使用新的隔离浏览器上下文，暖访问在同一上下文重访。服务器缓存、系统 DNS 和运营商路径不会被强制清空；主组禁用 Service Worker，不能代表已安装 PWA。点击路径沿用源页至少 5 秒观察和入口 2 秒停留的口径，不能称为立即点击。

DNS、TCP、TLS、HTTP、关键图片/字体/脚本失败、未完成的图片 decode、内容不可见、JS 异常和超时全部进入原始结果。失败样本不作为较快成功样本参与耗时汇总；冷访问失败后的暖访问也单独标注，不混入正常暖缓存汇总。只读导航和菜单交互，不登录、不填写或提交注册表单。页面自然发送的遥测和匿名会话请求照常执行，测试器不拦截请求或人为改变缓存；API 的非读取方法单独留账。

使用既有严格首屏就绪及原生 FCP/LCP/CLS/TTFB 观察，报告自定义内容就绪与点击就绪时刻；不把 `networkidle` 或 HTTP 成功当作首屏完成，不把短访问称为真实用户 INP。三轮仅提供观察性分布及逐次失败，不能作统计意义上的非退化保证。

## 本轮采集器的归因边界

原始 `summary.json` 按预先规则保守处理：任何关键资源异常都使样本退出严格成功统计。然而 `network.reset()` 仅重置请求账本，没有记录 CDP `loaderId` 或按新文档提交时刻分界；在重访等待 HTML 时，旧文档仍可能发起预加载请求。这些请求随后被导航取消，也会进入新样本的账本。原记录保留，不在看到结果后改为通过。

例如第一轮桌面学校邮箱注册页，两个被取消脚本发起于新导航后 13.122 / 13.199 秒，早于新 HTML 首字节 13.275 秒；目标页面仍在 13.902 秒满足可见、字体和图片就绪条件，且未记录 JS 异常。这强烈支持部分取消来自旧文档，但缺少 `loaderId`、initiator 和取消时间戳，不能逐条确证。学校页还有 `/monitoring` 的 429，应单列遥测限流，不能称为学校列表加载失败。

因此严格无告警子集的 p50/p75 可能受选择偏差影响，尤其慢 HTML 更容易留下旧页活动。补充统计分别列出无告警、仅有网络告警但内容已就绪、其他失败，并保留全部已就绪样本的描述性耗时；这不是把异常样本升级为成功。后续采集器要补充文档归属再验证，才能可靠计算页面加载失败率。本轮不改写既有工件，也不输出“全部性能通过”。

## 浏览器结果

正式采样时间为 2026-10-03 15:21:05–15:31:16 UTC（北京时间 23:21–23:31）。72/72 条样本完整，60 次文档访问及 12 次点击全部满足内容就绪条件；没有超时、JS 异常或缺失样本。原严格摘要为 52 次无告警、20 次资源告警，退出码 1，含义是 `OBSERVED_WITH_ERRORS`，不是采集进程崩溃，也不是“20 次页面打不开”。

前后浏览器 trace 均为 CN/LAX、IPv4/h2、目的端口 443、warp off、非缓存。3790 条资源记录中，3507 条有 HTTP 状态；其中 3487 条记录了目的端口，全部为 443/IPv4/h2，没有其他端口。20 条有状态但无端口，另有 283 条没有响应元数据，不能给这些记录补造直连证明。磁盘缓存标记 119 次、内存缓存标记 566 次、Service Worker 为 0；缓存标记可能重叠，不能直接相加当命中率。未观察到非读取方法的 API 请求。

浏览器实际观察到的 API 路径仅有匿名 `/v1/auth/me`：72 条记录中 68 条为预期的 401，4 条尚无响应元数据。没有观察到候选方案的 `/public/home` 聚合刷新路径，因此这轮不能验证改造后的动态数据刷新延迟；页面服务端内部 API 请求也不在浏览器账本里。

### 慢请求与告警

30 条关键资源取消告警包括 28 条脚本、1 条 CSS、1 条图片，均为 `ERR_ABORTED`；另有 3 条 `/monitoring` 429。它们分布在 20 个样本，不能把资源条数和样本数混用。没有改动 Sentry 配置。旧页请求归因限制见前文。

已完成请求的证据显示等待不只发生在大文件传输：第一轮桌面关于页约 1 KiB 的脚本等待响应头接近 11 秒；移动关于页约 8–9 KiB 的图片等待响应头接近 17 秒。第一轮桌面进入关于页时，约 920 KiB 的背景图片请求及 RSC 请求各持续约 26.9 秒；桌面暖注册入口的 HTML 首字节最慢 21.13 秒。这些是本条路径的现象，尚不能单凭浏览器时序在服务端、运营商和跨境链路之间确定根因。

**本轮可以确认当前线上站点能经这条大陆出口网络访问，但性能波动明显；不能据此承诺新方案性能不退化。** 未上线的独立静态 CDN 没有实际候选域名样本。后续验收需在真实候选域名与基线版本间交替比较，同时保留静态资源、API、冷/暖访问和失败结果；其他运营商、时间段和真实手机的覆盖也仍为空白。

## 波动原因定位：后续定向诊断

在原始 72 条记录之外，15:40–15:45 UTC 追加了 6 次串行公开 GET、4 次浏览器冷/暖文档观察及 8 次浏览器对照访问。前后实际浏览器探测仍为 CN/443；未修改应用、Sentry 或系统代理。新增证据位于 `artifacts/performance/network-cause-20261003/`，没有覆盖原始样本。

### 已确认的主要耗时

| 环节 | 证据 | 可以得出的结论 |
| --- | --- | --- |
| HTML 与静态资源交付 | 新冷 About 的 HTML 首字节 0.273 秒、全文约 0.290 秒；约 920 KiB 背景图传输约 8.07 秒；981 字节 JS 等响应头 8.145 秒 | 这次慢主要发生在 HTML 之后的资源交付阶段 |
| 缓存和连接 | 上述慢资源均 `x-vercel-cache: HIT`，全部复用同一个 HTTP/2 连接；实际 Web 响应为 `sin1` | 本例不是静态资源每次回源生成；Cloudflare 探测的 LAX 也不能当作 LiLink Web 节点 |
| 浏览器计算 | 原慢 About 样本图片解码约 17–22 ms，记录到的长任务总计 0–58 ms；新定向 About 没有长任务 | 未发现足以解释十几秒等待的图片解码或长任务；长任务总时长不等于完整 CPU 时间 |
| 注册 HTML | 线上响应 `private, no-cache, no-store`、`MISS`；单独串行 GET 约 0.29–0.30 秒，但浏览器重访曾等待首字节 9.25 秒 | 重访不能靠公共 HTML 缓存省掉请求，但 `MISS` 本身不能解释全部秒级等待 |

Vercel 的 `HIT` 表示响应来自其缓存，`x-vercel-id` 表示请求经过的区域；这不承诺到用户的传输时间。[Vercel 响应头定义](https://vercel.com/docs/headers/response-headers)。浏览器等待首字节包含网络与服务端准备时间，不能把整个等待都算成函数计算。[Chrome 网络时序定义](https://developer.chrome.com/docs/devtools/network/reference#timing-explanation)。

### 无关页面预加载会拖累当前访问

在注册页的定向诊断中，旧文档在导航后 3.909 秒发起 About 背景图预取，至 14.091 秒才完成。新注册 HTML 在 5.091 秒开始请求，至 14.344 秒收到首字节。两者有不同的文档 `loaderId`，但复用相同 HTTP/2 连接，等待高度重叠；这解释了为什么旧页预取可能影响后续访问，而不只是多用一些流量。

为验证这个因素，另做自然 → 阻止图集 → 阻止图集 → 自然的交错对照。每次新建隔离上下文，只在两个对照上下文用 CDP 阻止注册首屏不使用的 About 图集 URL，其余请求、浏览器缓存与页面保持自然行为。它是定位因素的实验，不是删除生产资源或新的性能通过验收。

| 顺序 / 条件 | 重访注册 HTML 首字节 | 重访内容就绪 |
| --- | --- | --- |
| 1 / 自然预加载 | 3.753 秒 | 4.323 秒 |
| 2 / 仅阻止 About 图集 | 0.083 秒 | 0.653 秒 |
| 3 / 仅阻止 About 图集 | 0.142 秒 | 0.818 秒 |
| 4 / 自然预加载 | 2.361 秒 | 2.940 秒 |

两组 HTML 都保持 `MISS`/`private`，浏览器静态缓存均仍生效；自然组确实下载约 942 KB 图集，对照组出现该 URL 的受阻记录。结果支持“无关大图预加载显著放大本轮重访延迟”，但每条件只有两次，不能把差值推广为全部用户的固定收益。HTTP/2 连接争用、传输队首阻塞是与现象一致的解释；尚未采集 TCP 重传或服务端排队证据，不能断言具体是运营商丢包、Vercel 调度或某个网络节点故障。

线上 HTML/JS/CSS 还支持“全局导航默认预取 About → RSC 资源提示 → 图集 preload”的触发链。注册初始 HTML 没有这张图，图集在 About RSC 返回后立即请求，早于 About CSS 完成及相关组件 JS 加载。首次小体积 RSC 正文和完整调用栈未保存，因此精确到该条资源提示的归因仍是强推断，详见 `source-mechanism-audit.json`。

### 正文显示策略放大资源延迟

从实际下载的线上源码确认：About 的 `main` 初始为 `data-image-ready=false`、`aria-busy=true`，正文通过 CSS 隐藏；客户端 JS 执行后才启动图片 decode 和 8 秒兜底。这个 8 秒从 `useEffect` 起算，不能覆盖此前 JS 下载等待。相关源码与工作树现有 `ImageReadyPage` 实现一致，但没有据此把 HEAD 当作生产提交。

例如原第一轮桌面 About：HTML 约 0.317 秒完整，关键 JS 约 11.317 秒完成，decode 约 11.385–11.403 秒，严格正文就绪约 11.658 秒。因此 JS 迟到会推迟正文显示，单独优化 360 ms 渐显无法消除前面的十几秒。严格就绪还要求字体、图片及透明度完成，并非整个页面此前都为空白。

本轮 About 的原生 LCP 最终候选实际为图标，并没有覆盖 CSS 背景图和全部正文；首页的最终候选也可能是按钮。这是同时保留语义内容就绪指标的原因，不能仅凭 LCP 推断正文已经完整呈现。

### 对方案选择的影响

优先处理无关预加载与“正文等待 JS 才显示”的依赖，有直接证据支持；独立 CDN 是否需要迁移全部静态资源，应与容量复测一起决定。按需失效主要解决再生成及回源频率，不能自动消除浏览器下载静态文件的请求和传输，也不能自动解除当前显示依赖。现有证据没有把监控 429 或 ISR 额度耗尽确定为上述慢样本的主因。

这轮只做诊断，没有据此修改加载策略。定向实验源码、脱敏时序、线上源码哈希与复核记录在上述工件目录，`diagnostic-manifest.json` 固定诊断脚本摘要及对照结果；`direct-network-20261003/bottleneck-analysis.mjs` 可从原 72 条记录离线重建分段分析。

在相同网络前提下，分别运行 `python3 artifacts/performance/network-cause-20261003/curl-probe.py`、`node artifacts/performance/network-cause-20261003/browser-diagnostic.mjs` 和 `node artifacts/performance/network-cause-20261003/atlas-control/run.mjs` 可复现方法。这三个现场诊断脚本会更新各自的输出，重跑前应保留本轮目录副本；不要与其他性能负载同时运行。`source-mechanism-audit.json` 及 `offline-crosscheck.json` 为本轮源码与时序核对工件。
