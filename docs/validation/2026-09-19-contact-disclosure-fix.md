# 联系方式公开权限修复与验收

日期：2026-09-19 至 2026-09-20 凌晨。联系方式修复和自动化全量回归已完成；安装版 Safari、Chrome 已直接操作用户端、后台及商户端。Safari 续测新发现的后台资料保存失败也已修复，并在两款浏览器复验。仍不宣称所有按钮及所有条件分支达到 100% 覆盖，具体缺口列于下文。没有提交、推送或部署。

## 问题与修复

问题发生在匹配已经准备好、其中一人被暂停、随后轮次揭晓的场景。引荐服务会正确跳过该配对并保留 `introducedAt = null`，但 Dashboard 曾把 `revealedAt` 当作公开联系人的兜底条件，从用户资料读取当前微信或邮箱，导致当前匹配和历史卡片仍可能公开联系人。

本次修改：

1. `apps/api/src/common/dashboard/dashboard-snapshot.service.ts`：公开联系人只认 `introducedAt`，移除从揭晓时间和实时联系方式推导授权的兜底；未引荐记录在用户快照中统一为 `UNMATCHED`，读取旧快照时也返回空匹配，不下发对方资料。
2. 当前匹配 `match-client.tsx` 与历史组件 `MatchHistoryList.tsx` 使用同一判断。未引荐时复用普通未匹配状态：当前页显示「本轮未匹配到对象」，历史卡片显示「未匹配到」。没有信封、对方资料、分数、复制或举报入口，首页也不显示配对成功；保留正常引荐的冻结值及合法旧邮箱兼容。
3. 新增迁移 `20260919090000_authorize_legacy_match_contacts`：以首次成功秋季迁移 `20260911120000_account_deletion` 的 `started_at` 为边界，只为此前已揭晓、恰好两名有效参与者、均为 ACTIVE、有效报名且有意向、没有屏蔽或举报的旧记录冻结联系人并设置引荐时间。不会给新流程跳过引荐的记录补授权，不补发邮件，不覆盖已有引荐。授权、冻结和旧快照清理在同一事务内完成。
4. 同一历史组件的手机回归发现长轮次名使页面横向溢出 6px；通过限制 grid 最小列宽和允许标题换行修复，并补充 Storybook 场景。

5. Safari 后台编辑用户介绍报 `property headline should not exist`。补齐 `AdminUpdateUserDto` 的 `headline/bio/schoolYear/programName` 四字段、长度和类型限制及显式清空；`AdminService.updateUser` 在同一事务中更新账号并创建或更新资料，保留注销账号保护，记录实际变更字段并同步匹配快照。新增 6 条 DTO 回归及 3 条 PostgreSQL 资料创建、更新、清空和注销保护回归。Safari 与 Chrome 均实际保存四项字段并回读。

自动邮件规则没有改为人工审核：到点揭晓后系统检查双方状态，通过则设置 `introducedAt`、冻结联系人并在同一事务内创建两封邮件，由邮件队列自动发送。揭晓前有人被暂停则这一对被跳过，双方均没有生成匹配邮件。`introducedAt` 表示已允许引荐且邮件已入队，不表示邮件一定已投递成功。

兼容迁移的边界：没有成功迁移记录时不授权；旧版本在该时间边界之后才揭晓的记录也会保守保持隐藏。迁移在执行期间锁住相关表的写操作，发布时应安排执行窗口。此次只在隔离数据库验证，没有执行生产迁移。

## 9 月 20 日追加：未引荐统一按未匹配展示

按最新产品要求，用户端不再说明未完成引荐或暂停原因。API 新快照、旧缓存读取、当前轮次成功标记和历史记录统一转换；前端也规范化旧数据，复用既有未匹配组件。保留原始 Match 和参与记录，未引荐时不产生匹配邮件。

引荐事务新增内部审计 `match.introduction_skipped`，记录轮次、配对和具体参与者原因，例如 `SUSPENDED`；屏蔽、注销、报名失效等有各自原因。审计与揭晓同事务，重复揭晓不会重复记录。历史取消记录不依据今天的账号状态猜测、补写过去原因。

此次重新执行：API 578/578、PostgreSQL E2E 85/85、前端单元 88/88、Storybook 231/231，共 982 条通过；API/Web/Storybook 类型检查、API/Next 构建、针对性 lint 和 diff 检查通过。数据库先出现 4 条旧语义断言失败，已更新未引荐预期，并将注销并发场景明确设为已成功引荐，以继续验证注销隐私保护；最终全量在新建空测试库通过。测试覆盖暂停后揭晓、污染旧缓存、恢复账号、重复揭晓、双方结果一致、零封邮件与一次暂停审计。
