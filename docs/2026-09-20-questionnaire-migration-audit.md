# 新旧问卷与历史答案迁移审计

> **文档归属**：遵循 [文档总纲](README.md)。本文件是 2026-09-20 的只读审计与修复建议，补充并修正 [秋季发布计划](2026-09-20-autumn-release-plan.md)。不是已完成的迁移或上线验收。

> **后续用户决定**：采用 [旧数据保留、全部用户重新填写新版](2026-09-20-questionnaire-reset-plan.md)。本文第 2–4 节保留发现时的事实和候选建议，其中旧答案转换、预填和局部补填建议不再作为执行口径；全部旧答案/草稿独立归档，账号与最近三轮匹配继续保留。

## 1. 结论与审计范围

**当前不能按“保留旧答案、只补三道生活习惯题”直接发布。** 题目选项、必填规则、对方偏好的表达方式和 VIP 权限均有变化，现有迁移没有完成这些语义变化的衔接。此前发布计划对这部分判断不完整，以本审计为准。

已经对照：生产数据库两个问卷版本和答案聚合、生产 API 提交 `6606496ea38a2a089fc550d79544e471bd058bd9`、生产前端提交 `99bca86f17d9b350e8c4c8350404c2ee64732a87`、候选 `main=d05eb891606d16d1902ffd79cf09223a73992836` 的前端回填/交互、API 读取/保存/报名、共享匹配解析、题库 seed 和 43 条迁移。

审计覆盖旧 21 个硬匹配字段、新增 3 个对方生活习惯偏好、线上 21 道价值观题、新增 3 道自身生活习惯题，以及账号关联、草稿、历史答案和退役字段。没有下载用户答案明细、联系方式或身份信息；生产查询使用只读事务，返回题目定义及聚合数量。

## 2. 发布前必须处理的变化

### P1：颜值自评从三个类别改成 1–10 分，全部旧答卷都没有可直接回填的值

生产分布为“普通人”136 份、“小帅/美”87 份、“顶帅/美”19 份。新版 `HARD_MATCH_LOOKS` 只接受字符串 `"1"` 至 `"10"`，对应滑块。迁移 SQL 没有转换这两个枚举。

实际代码反例：旧共享解析器接受旧答案；新版解析器拒绝；前端回填把自评变为空，滑块显示未选择。API 读取失败后保留原硬字段，却按“非空”判断必填完整性，出现 `missingRequired=false` 与前端空值不一致。选项签名仍可能提示“有更新”，不能据此认定不存在提示，也不能把签名当成有效答案校验。

**处理建议**：保留旧类别原值，全部 242 份（其中真实活跃 238 份）由用户重新自评；不擅自把三个类别映射为 3/6/9 分。迁移状态应明确是“旧格式待重答”，API、资料页和报名门槛使用同一判定。

证据：[共享枚举与解析](../packages/shared/src/hard-match.ts) 第 3、700 行；[前端回填](../apps/web/src/lib/hard-match.ts) 第 152 行；[资料页](../apps/web/src/app/dashboard/profile/profile-client.tsx) 第 1399 行；[读取和提醒](../apps/api/src/modules/account/account.service.ts) 第 719、1212 行。

### P1：对方颜值从类别多选改成“最低分”，不能等价转换

旧 `hard_partner_looks` 是三个类别的任意非空子集；新版 UI 表示“n 分及以上”，交互后写入连续的分数集合。242 份旧数组都无法直接复用，其中 146 份原来有颜值限制，其余选择全部类别。

当前回填会过滤掉旧类别，再把空数组兜底为全部 1–10 分，页面等同“1 分及以上”。这不能表达原用户已经确认放宽偏好。普通账号还会受到 VIP 权限变化影响。

**处理建议**：旧限制原样归档；有资格使用该筛选时要求重新选择最低分。普通账号明确告知该筛选需 VIP、当前不生效，保留原值供后续确认，不能借回填默认值记录一次新的用户选择。

另有 **P2 的新契约问题**：API 仍接受 `["5","8"]` 这类不连续数值集合，UI 却显示“5 分及以上”；不操作滑块时可能继续保存原稀疏集合。合成数据已复现；生产暂时全为旧类别，并无已发现的数值稀疏实例。后续应统一为最低分字段，或限制数组必须是连续后缀；旧任意集合不可静默扩大。

证据：[资料页初始化及最低分滑块](../apps/web/src/app/dashboard/profile/profile-client.tsx) 第 394、1627 行；[表单转答案](../apps/api/src/modules/questionnaire/hard-match.ts) 第 458 行。

### P1：三个多选题从“最多 3 项”变成“必须 3 项”

旧 API 接受 1–3 项；新版完整提交要求数量恰好等于 `selectionLimit`。线上题目定义没有换 key 或选项，但校验行为改变了。

| 题目 | key | 只选 1 项 | 只选 2 项 | 需要补选 |
| --- | --- | ---: | ---: | ---: |
| 最打动你的加分项 | `green_flags` | 13 | 19 | 32 |
| 喜欢的约会方式 | `ideal_date_style` | 13 | 15 | 28 |
| 希望关系最终像什么 | `future_picture` | 21 | 31 | 52 |

去重后影响 **71 份，其中真实活跃 67 份**。这三题现有答案没有非法选项或重复值，问题是选项数量不足。读取会保留已有选项并标为待补全；完整保存只会形成草稿，直到满足新版要求。

**处理建议**：若坚持新版“恰好 3 项”的规则，只让这 71 份补足缺少的项，其余已选内容保留。不能随机补选，也不能把全部多选题清空要求重做。

证据：[完整校验](../apps/api/src/modules/questionnaire/questionnaire.service.ts) 第 197 行；[选项规范化](../apps/api/src/modules/questionnaire/questionnaire-config.ts) 第 205 行；[前端数量要求](../apps/web/src/app/dashboard/profile/profile-client.tsx) 第 1871 行。

### P1：体重、介绍、新增必填题和报名门槛没有统一

| 项目 | 规则变化或现状 | 需要处理 |
| --- | --- | --- |
| 自己的体重 | 从选填变必填；85 份缺失，其中 81 份为真实活跃账号 | 原有有效公斤数保留，缺失用户补填；不估算体重 |
| 一句话介绍 | 完整保存从允许空改为必填；11 份为空 | 补填；共享匹配解析器在旧版已经拒绝空介绍，不把原有资格限制说成新回归 |
| 锻炼、吸烟、饮酒 | 新增 3 道必填单选；所有旧答卷都没有 | 由用户填写；不能默认“不吸烟”“不饮酒”或“很少锻炼” |
| 当前题库的其他必填项 | 保存校验完整题库；无草稿报名只校验部分硬字段 | 修复统一校验后才能保证旧用户补完再报名 |

合成反例已调用真实 `AccountService.assertQuestionnaireReadyForOptIn`：用合成数值颜值隔离其他因素后，没有草稿的已提交答卷即使缺体重、缺三道生活习惯题、甚至缺旧的 `values` 题，也能通过此门槛；有 1 项加分项的答卷同样通过。完整保存路径会将不完整提交保存为 DRAFT。撮合资格筛选也依赖共享硬字段解析，不能替代当前题库完整性校验。

**边界**：当前生产旧自评会先被新版拒绝，掩盖上述后续问题；这不代表现有 242 份原始旧答案现在已经能绕过全部检查。门槛反例在合成内存服务中验证，尚未通过 HTTP/浏览器/迁移后的真实数据库复验。

**处理建议**：完整提交、报名、撮合资格、首页进度和待补全列表共享当前版本验证结果；无草稿也必须验证，不能仅看 `submittedAt`。保留旧提交快照，但待重答/补填完成前不进入新轮撮合池。

证据：[API 必填字段](../apps/api/src/modules/questionnaire/hard-match.ts) 第 788、892 行；[报名门槛](../apps/api/src/modules/account/account.service.ts) 第 1655 行；[撮合资格](../apps/api/src/modules/cycles/cycles.service.ts) 第 1324 行。

### P1：旧高级偏好转为 VIP 后，普通用户保存会覆盖原值

新增 VIP 规则包括对方颜值、身高、体重、学校/学校性别排除和锻炼频率。上线时新 VIP 表为空，旧账号不会自动获得 VIP。

已有偏好分布：有限制的身高 241 份、体重 108 份、颜值 146 份、学校或学校性别排除 147 份；按这四类去重，242 份均至少有一项原偏好。

权限层不让非 VIP 使用高级筛选，是当前产品行为；但 `saveQuestionnaire` 在写入前应用 `effectivePreferenceForm`，会将这些原值改成不限，再覆盖唯一的答卷记录。合成测试已走真实完整保存方法，截获 upsert：175 cm 下限被改为 120 cm，数值颜值限制被替换为全部分数，学校排除和体重区间也在规范化中清空。

**处理建议**：区分“用户保存的偏好”与“本轮有权生效的偏好”；失去权益只影响生效计算，原偏好保留，重新获得权益时按新版格式确认后生效。不能宣称当前代码已经做到“只停用、不丢失”。不在迁移中自动发放 VIP 来绕过问题。

证据：[权益与生效过滤](../packages/shared/src/profile-preferences.ts) 第 15、42、61 行；[完整保存](../apps/api/src/modules/account/account.service.ts) 第 1075、1125 行。

### P2：国籍、语言已从页面与匹配规则退出，但旧字段还会回填默认值

自己国籍/语言和对方国籍/语言四个控件已移除，匹配兼容判断也移除了两类限制。旧答卷有 67 份国籍偏好、61 份语言偏好；这些选择在新版将不再用于筛选，需要向用户说明规则变化。

另有 33 份没有自己的国籍/语言。表单仍会填入“中国/中文”默认值，完整保存可能写入用户本次无法在页面确认的字段。默认机制早已存在，但现在控件隐藏，不能再将这些默认值当成新问卷确认的身份事实。

**处理建议**：明确退役四字段的用途，保留原始历史；新提交不补造缺失身份字段，界面说明相关旧限制已停止使用。已保存的非默认值不能被统一重写。

证据：[前端回填](../apps/web/src/lib/hard-match.ts) 第 152 行；[匹配兼容规则](../packages/shared/src/hard-match.ts) 第 935 行。旧限制阻止的合成跨国籍/语言组合在新版可兼容，已用真实旧/新解析与匹配函数核验。

这里的“兼容”指查询时的类型、选项集合和候选数量要求检查，不代表整个答卷已经满足新增题、自评、体重等要求。7 道多选题的现存选项均合法且无重复。

候选服务将题库的 `required` 一律改为 true，完整校验也不再接受选填。当前线上 21 题本来全为必答，未发现这项变化新增影响；若以后引入自定义选填题，此行为仍需统一到题库契约，不能忽略数据库标志。

## 4. 题库来源、草稿和历史记录

### 4.1 生产题库不等于本地 seed

两个 seed 都包含 24 道旧默认题 + 3 道生活习惯题，合计 27 题；当前生产迁移应得到 24 题。静态提取常量对照结果如下，没有执行任何 seed。

| 差异 | 线上当前 / 现有迁移 | 本地 seed |
| --- | --- | --- |
| `values` | 无数量上限 | 限制 4 项 |
| `red_flag_sensitivity` | 无数量上限 | 限制 3 项 |
| `shared_growth_topics` | 无数量上限 | 限制 3 项，顺序由 18 变 21 |
| `feeling_cared_for` | 无数量上限 | 限制 3 项 |
| `support_need`、`admired_partner_traits`、`small_happiness` | 当前题库无这 3 题 | 会重新加入 |
| `future_picture` | 顺序 21 | 顺序 22 |
| 文案 | 线上多选已采用“几个/哪些” | 多题仍写固定数量；两个 seed 自身还有引号样式差异 |

`scripts/seed-defaults.mjs` 更新原当前版本，并删除不在默认列表中的题；`prisma/seed.ts` 检测不同后创建新的当前版本，但仍切换到默认题库。两者均不适合作为本次生产升级入口。只换 seed 实现并不能解决题库内容分叉。

**建议**：生产最终题库以线上当前版本和经过确认的增量为基准，建立同源定义；测试库应使用这一发布题库，另保留历史 21 题 fixtures。否则在 27 题测试库通过，并不能证明线上 21→24 题迁移通过。

证据：[seed-defaults](../apps/api/scripts/seed-defaults.mjs) 第 71、311、369 行；[Prisma seed](../apps/api/prisma/seed.ts) 第 225、492、522 行；[版本化迁移](../apps/api/prisma/migrations/20260920101000_add_lifestyle_questionnaire_revision/migration.sql)。

### 4.2 草稿不能只套用新版清洗后覆盖

10 份未提交草稿中，8 份有旧类别自评、5 份有旧对方颜值集合，8 份没有体重。6 份还缺少后来加入的国籍、语言和体重等草稿字段。新版草稿清洗过滤旧颜值，下一次自动保存可能把清洗后的空值写回草稿。

应保存迁移前原始草稿，明确每个失效字段的旧值及待重答原因；合法软答案仍回填，不要求从第一题重做。合成完整保存测试也确认：不满足要求时返回 DRAFT，仅更新草稿，不覆盖此前已提交答案。这一正确行为应保留。

### 4.3 退役答案与唯一答卷记录

数据库仍有 `support_need`、`admired_partner_traits`、`small_happiness` 的历史答案：每个 key 各见于 2 条记录，其中 1 条为真实活跃账号。没有读取其内容，也不能按“线上题库已无此题”断言它们全是测试数据。

API 按当前题库过滤这些 key；前端提交当前题目后，唯一答卷记录整体更新，旧 key 不再存在于当前答案。直接向保存 API 发送未知 key 则有未知题目校验，不能依赖“把旧 JSON 全量传回”保存历史。

`QuestionnaireResponse.userId` 唯一，无独立逐次答卷历史表。现有迁移不改旧答案，不等于用户再次保存后旧答案仍可追溯。建议迁移前保存受限、加密、可恢复的原始版本/答案/草稿备份；应用如需长期追溯，另设有明确保留期限的答卷历史或迁移归档，不把退役答案塞入公开资料页。

56 份已提交答卷没有硬字段确认签名；185 份有自评签名、182 份有对方颜值签名。签名表示旧选项集是否确认，不是值转换表；不能批量写入新版签名冒充用户已重答。

账号 ID、登录邮箱、密码散列、学校和真实联系方式保持原关联，不重建账号。只读检查中真实活跃账号的首选联系方式无格式异常；1 个昵称不足两字的账号应走资料补全，不因其未完成资料而删除账号。

## 5. 按用户决定调整后的实施与验收

执行 [全量重填与历史保留方案](2026-09-20-questionnaire-reset-plan.md)，其验收替代原局部补填方案：

1. 原样归档旧问卷、答案、草稿、签名与时间；核验完成后建立独立新版活动状态，不回填旧字段。
2. 账号资料保留；未完成新版仍能查看最近三个已揭晓轮次，历史卡片重建不依赖空白新问卷。
3. 新版完整提交、明确报名、撮合资格使用统一的当前版本和完整性校验；旧提交不再视为已完成。
4. 保留历史权限、举报屏蔽和业务关联；新问卷的 VIP 偏好保存及最低分表示问题仍需修复。
5. 完成隔离迁移、恢复与旧用户真实链路验收后再发布；本审计的 14 组行为反例不能代替新方案验收。
